# Phase 00 real-service transition

Status: **in progress**. The earlier Phase 00 acceptance covered a local synthetic baseline. It is not evidence of private staging or real-provider acceptance.

On 2026-09-26, a fresh isolated Compose project (`project-junction-phase00`) passed `COMPOSE_PROJECT_NAME=project-junction-phase00 pnpm test:integration` with the local fixture environment: both migration deploys, auth migrations, compatibility/upgrade/restore/lock/rollback checks, 49 PostgreSQL and media integration tests, and the built API/worker synthetic regression smoke. This proves the local regression path after the real-service code changes. It does not prove Better Auth, Resend, Sumsub, VPS, or private HTTPS staging acceptance.

## Implemented boundary

- Staging authentication uses Better Auth with PostgreSQL-backed users and sessions. Email verification and password recovery send through Resend. TOTP enrollment, a second-factor sign-in challenge, and backup-code recovery use Better Auth's two-factor plugin. A verified TOTP or backup-code session creation binds MFA and recent-auth timestamps to the matching Junction session. The API and realtime gateway derive identity from the Better Auth cookie, and every staging authorization context rechecks the matching Better Auth session and verified email in PostgreSQL so sign-out or expiry denies an existing realtime socket. The foundation bridge creates an unverified Junction identity. Verified email alone grants no adult capabilities.
- API and worker processes require PostgreSQL and staging mode outside test processes. Production web builds require staging mode and same-origin `/v1` browser API routing. Staging startup also requires configured real auth, email, identity, object storage, and malware scanning adapters. Staging denies the synthetic account, staff, demo-session, and fake provider callback entry points that have been explicitly gated. Public catalog queries select real workspaces in staging. The worker claims only media processing events in staging; it leaves other outbox events pending until their real delivery handlers are implemented, instead of recording a false delivery receipt. The local fake external-effect receiver is disabled in staging.
- New authenticated accounts enter one shared real marketplace workspace so applications can reach a common review queue. A Vendor application scopes the same Better Auth-backed Junction session to its new Owner membership, and a later sign-in restores that scope when exactly one Owner membership is eligible. A user with multiple Owner memberships can select one through the authenticated staging API and Vendor workspace after recent MFA; each change is audited and membership checked inside a transaction. Existing real workspaces created before this change require a migration plan before staging is populated; no such migration has been run. Real Platform reviewer grants are stored in PostgreSQL and can be provisioned or revoked by a staging operator after Better Auth email and Sumsub adult verification. Grant and revocation write audit rows. Reviewer mutations require recent MFA.
- Staging Customer discovery, Vendor workspace, and Platform review use the account cookie and no longer ask users to paste session IDs. Vendor application responses omit the internal session ID in real workspaces; the synthetic test result retains it for regression fixtures.
- An authenticated staging user can open Sumsub's WebSDK from the account page. Token issuance and refresh call the same-origin API. The adapter signs API requests, verifies webhook digests, and records sandbox review, reset, hold, level-change, deactivation, deletion, and activation events in the durable provider inbox. Signed deactivation or deletion immediately revokes adult access, and later reconciliation cannot restore it from an older approval event. Activation triggers a fresh provider read before access can return. The worker checks Sumsub's current applicant and review before granting or rejecting adult status. Manual test webhooks are rejected. The worker's grant path remains disabled until `SUMSUB_AGE_18_LEVEL_CONFIRMED=true` is set after the sandbox level and permissions are inspected.

## Private staging setup

1. Point a new staging hostname at the existing VPS and install the [private Caddy ingress](../deployment/STAGING-DEPLOYMENT.md). It routes the web auth route and API under the same HTTPS origin, protects browser routes with Basic authentication, and exposes only the signed Sumsub webhook callback. Set `BETTER_AUTH_URL` to that origin; set `NEXT_PUBLIC_JUNCTION_RUNTIME_MODE=staging` and `NEXT_PUBLIC_JUNCTION_API_URL=/v1` at web build time; configure `DATABASE_URL`, `BETTER_AUTH_SECRET` (at least 32 random characters), and `JUNCTION_RUNTIME_MODE=staging` in the deployment secret store. Allow Sumsub's frame, camera, and microphone in the staging host's security headers. Apply the existing database migrations, then run `pnpm db:auth:migrate` against the staging database, including the TOTP migration.
2. Verify the sending domain with Resend. Set `RESEND_API_KEY` and `RESEND_FROM_EMAIL` in the deployment secret store. Confirm a real mailbox receives verification and recovery messages.
3. Create a Sumsub sandbox verification level that enforces age 18 or older, and obtain sandbox application token with View applicants permission, API signing secret, and a distinct webhook digest secret. Set `SUMSUB_AGE_LEVEL`, `SUMSUB_APP_TOKEN`, `SUMSUB_SECRET_KEY`, and `SUMSUB_WEBHOOK_SECRET` in the deployment secret store. Configure signed `applicantReviewed`, `applicantReset`, `applicantOnHold`, `applicantLevelChanged`, `applicantDeactivated`, `applicantDeleted`, and `applicantActivated` webhooks. After inspecting the level's age rule and completing a sandbox approve, reject, reset, deactivation, activation, deletion, and replay rehearsal, set `SUMSUB_AGE_18_LEVEL_CONFIRMED=true` for the worker. Never put secret values in the repository or chat.
4. After applying `prisma/migrations/20260925000000_real_platform_reviewer_grants`, sign in the invited reviewer, verify email, complete Sumsub, and enroll MFA. Set `STAGING_REVIEWER_EMAIL` and `STAGING_OPERATOR_LABEL` in the host's protected environment and run `pnpm staging:reviewer grant`. Use `pnpm staging:reviewer revoke` to remove access. The CLI requires `JUNCTION_RUNTIME_MODE=staging` and `DATABASE_URL`; do not run it against the portfolio or local database. Verify queue access and a fresh MFA challenge; then revoke and verify denial without changing application, audit, or outbox state.

## Open acceptance gates

- Configure and verify the Sumsub age-18 level and its permissions, then exercise live signed webhook retries and revocation. The worker's code checks current applicant identity, level, status, and decision, but those checks cannot prove the level's actual age rule until the Sumsub account is configured and inspected. A sandbox `GREEN` result alone does not establish age 18 without that configuration.
- Verify the Better Auth second-factor session binding end to end on private staging. Enrollment or a general signed-in cookie alone must not set MFA and recent-auth timestamps; test challenge failure, backup-code recovery, trusted-device behavior, and the 15-minute freshness limit.
- Replace or disable remaining synthetic provider effects, local-only media dependencies, fixture-based discovery and catalog behavior, and any local-only operational path before a staging release. The current staging mode is **not deployable as a complete real-service flow**.
- Prove reviewer grant, MFA freshness, revocation, and cross-Vendor review on the private staging host. The database and CLI path are implemented but have not been exercised on staging.
- Exercise the multi-Owner role switch on private staging, including MFA expiry, revoked membership, a foreign Vendor ID, and the Customer-scope return path. The transaction and UI have local checks but no provider-backed staging acceptance yet.
- Exercise sign-up, mailbox verification, login, recovery, expired session, realtime authorization, identity check, denial, and revocation end to end on the private HTTPS host with real sandbox accounts. No such staging proof has been recorded yet.
- Configure the exact staging DNS name, Caddy credentials/upstreams, isolated VPS services and secrets, and provider accounts. The ingress file is prepared but has not been validated on or installed into the VPS.
