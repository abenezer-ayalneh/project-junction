## Implemented boundary

- Staging authentication uses Better Auth with PostgreSQL-backed users and sessions. Email verification and password recovery send through Resend. TOTP enrollment, a second-factor sign-in challenge, and backup-code recovery use Better Auth's two-factor plugin. A verified TOTP or backup-code session creation binds MFA and recent-auth timestamps to the matching Junction session. The API and realtime gateway derive identity from the Better Auth cookie, and every staging authorization context rechecks the matching Better Auth session and verified email in PostgreSQL so sign-out or expiry denies an existing realtime socket. The foundation bridge creates an unverified Junction identity. Verified email alone grants no adult capabilities.
- Better Auth 1.7.6 creates a replacement session while confirming initial TOTP enrollment. The session hook now skips that existing-session path and marks recent MFA only for a new sign-in challenge session. An isolated PostgreSQL probe called the actual Better Auth endpoints: password sign-in and TOTP enrollment left Junction MFA timestamps unset; TOTP and backup-code sign-in challenges set them on their matching sessions. This is local integration evidence and does not replace a private-staging browser and mailbox journey.

A timestamped `legacy_verified_compat` record is denied in staging, and migration `20260928000000_retire_legacy_adult_default` changes the database default to `unverified` so old writers cannot create adults by omission. Explicit legacy records remain usable only by synthetic regression tests. 2. Verify the sending domain with Resend. Set `RESEND_API_KEY` and `RESEND_FROM_EMAIL` in the deployment secret store. Confirm a real mailbox receives verification and recovery messages.
3. Create a separate Didit Sandbox application and an age-18 workflow. Store `DIDIT_API_KEY`, `DIDIT_WEBHOOK_SECRET`, and `DIDIT_WORKFLOW_ID` in the deployment secret store. Register the signed `status.updated` webhook at `/v1/identity/didit-webhook`, then complete an approve, decline, status replay, and callback reconciliation rehearsal before setting `DIDIT_AGE_18_WORKFLOW_CONFIRMED=true` for the worker. 4. Generate MinIO root and application credentials with `prepare-minio-secrets.py`, configure its separate DNS hostname and digest-pinned server/client images, then verify signed upload, download, deletion, and bucket-policy denial through Caddy.
5. After applying `prisma/migrations/20260925000000_real_platform_reviewer_grants`, sign in the invited reviewer, verify email, complete Didit, and enroll MFA. Set `STAGING_REVIEWER_EMAIL` and `STAGING_OPERATOR_LABEL` in the host's protected environment and run `pnpm staging:reviewer grant`. Use `pnpm staging:reviewer revoke` to remove access. The CLI requires `JUNCTION_RUNTIME_MODE=staging` and `DATABASE_URL`; do not run it against the portfolio or local database. Verify queue access and a fresh MFA challenge; then revoke and verify denial without changing application, audit, or outbox state.
