## Implemented boundary

- Staging authentication uses Better Auth with PostgreSQL-backed users and sessions. Email verification and password recovery send through Resend. TOTP enrollment, a second-factor sign-in challenge, and backup-code recovery use Better Auth's two-factor plugin. A verified TOTP or backup-code session creation binds MFA and recent-auth timestamps to the matching Junction session. The API and realtime gateway derive identity from the Better Auth cookie, and every staging authorization context rechecks the matching Better Auth session and verified email in PostgreSQL so sign-out or expiry denies an existing realtime socket. The foundation bridge creates an unverified Junction identity. Verified email alone grants no adult capabilities.
- Better Auth 1.7.6 creates a replacement session while confirming initial TOTP enrollment. The session hook now skips that existing-session path and marks recent MFA only for a new sign-in challenge session. An isolated PostgreSQL probe called the actual Better Auth endpoints: password sign-in and TOTP enrollment left Junction MFA timestamps unset; TOTP and backup-code sign-in challenges set them on their matching sessions. This is local integration evidence and does not replace a private-staging browser and mailbox journey.
- Staging adult authorization now requires the explicit `verified` lifecycle state and a verification timestamp. A timestamped `legacy_verified_compat` record is denied in staging, and migration `20260928000000_retire_legacy_adult_default` changes the database default to `unverified` so old writers cannot create adults by omission. Explicit legacy records remain usable only by synthetic regression tests. A focused PostgreSQL check and the populated-upgrade check passed; the migration was applied to the empty VPS staging database and its default and migration record were verified directly.
- API and worker processes require PostgreSQL and staging mode outside test processes. Production web builds require staging mode and same-origin `/v1` browser API routing; the Compose web process also checks Better Auth, Resend, and isolated API/database configuration before starting. Staging startup requires configured real auth, email, identity, object storage, and malware scanning adapters. The API no longer registers synthetic account, staff, demo-session, or fake-provider callback entry points, and it no longer permits the retired `X-Junction-Session` transport header. Public catalog queries select real workspaces in staging. The worker now claims real-workspace media and catalog outbox events, appends them to the isolated Redis domain-event stream with atomic event-ID deduplication, then acknowledges PostgreSQL. Synthetic workspaces and synthetic foundation event types are excluded. The former in-memory worker outbox, provider inbox, session registry, idempotency store, and fake external-effect receiver are removed from application runtime code. The API RealtimeGateway subscribes to `junction:staging:domain-events-live`, resolves each event from PostgreSQL, and emits only validated public catalog changes to authenticated workspace sockets.
- Staging API CORS derives its only allowed browser origin from `BETTER_AUTH_URL`; an override that includes localhost or another origin fails startup. Local test mode retains its localhost defaults.
- Staging does not register the synthetic account, demo, audit-marker, Staff fixture, or fake-provider webhook controller. The ingress also returns 404 for those paths before account authentication. Its OpenAPI document omits those routes, synthetic schemas, and the session-header security scheme; real routes document the Better Auth cookie. The local regression controller and contract retain the test-only routes. A served Nest test verified staging route absence and local test route presence; the rebuilt API passed its package build.

The staging API exposes `POST /v1/identity/didit-webhook` while omitting synthetic routes. This code boundary has local regression coverage; it does not prove provider-backed staging acceptance.
