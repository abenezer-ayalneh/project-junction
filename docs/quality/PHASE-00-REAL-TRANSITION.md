## Implemented boundary

- Staging authentication uses Better Auth with PostgreSQL-backed users and sessions. Email verification and password recovery send through Resend. TOTP enrollment, a second-factor sign-in challenge, and backup-code recovery use Better Auth's two-factor plugin. A verified TOTP or backup-code session creation binds MFA and recent-auth timestamps to the matching Junction session. The API and realtime gateway derive identity from the Better Auth cookie, and every staging authorization context rechecks the matching Better Auth session and verified email in PostgreSQL so sign-out or expiry denies an existing realtime socket. The foundation bridge creates an unverified Junction identity. Verified email alone grants no adult capabilities.
- API and worker processes require PostgreSQL and staging mode outside test processes. Production web builds require staging mode and same-origin `/v1` browser API routing; the Compose web process also checks Better Auth, Resend, and isolated API/database configuration before starting. Staging startup requires configured real auth, email, identity, object storage, and malware scanning adapters. Staging denies the synthetic account, staff, demo-session, and fake provider callback entry points that have been explicitly gated. Public catalog queries select real workspaces in staging. The worker now claims real-workspace media and catalog outbox events, appends them to the isolated Redis domain-event stream with atomic event-ID deduplication, then acknowledges PostgreSQL. Synthetic workspaces and synthetic foundation event types are excluded. The local fake external-effect receiver is disabled in staging. No downstream stream consumer is implemented yet.
- Staging API CORS derives its only allowed browser origin from `BETTER_AUTH_URL`; an override that includes localhost or another origin fails startup. Local test mode retains its localhost defaults.
- Staging does not register the synthetic account, demo, audit-marker, Staff fixture, or fake-provider webhook controller. The ingress also returns 404 for those paths before account authentication. Its OpenAPI document omits those routes, synthetic schemas, and the session-header security scheme; real routes document the Better Auth cookie. The local regression controller and contract retain the test-only routes. A served Nest test verified staging route absence and local test route presence; the rebuilt API passed its package build.
- The staging API dependency graph installs a rejecting synthetic provider adapter, so the fake payment callback adapter is not constructed even if a route reaches the service. Local regression tests still construct the fake adapter explicitly.

- Staging API and worker startup require Redis fanout configuration; the checked-in local Redis fixture URL is rejected. API health awaits the initial Redis adapter connection. Sustained Redis availability and cross-process realtime delivery remain staging acceptance checks.
- The default `.env.example` is now a fail-closed staging template with required secrets unset. The former local synthetic values live in `.env.integration.example` for regression tests only; an existing ignored `.env` is not changed by this repository edit.

- New authenticated accounts enter one shared real marketplace workspace so applications can reach a common review queue. A Vendor application scopes the same Better Auth-backed Junction session to its new Owner membership, and a later sign-in restores that scope when exactly one Owner membership is eligible. A user with multiple Owner memberships can select one through the authenticated staging API and Vendor workspace after recent MFA; each change is audited and membership checked inside a transaction. Existing real workspaces created before this change require a migration plan before staging is populated; no such migration has been run. Real Platform reviewer grants are stored in PostgreSQL and can be provisioned or revoked by a staging operator after Better Auth email and Sumsub adult verification. Grant and revocation write audit rows. Reviewer mutations require recent MFA.
- Staging Customer discovery, Vendor workspace, and Platform review use the account cookie and no longer ask users to paste session IDs. Vendor application responses omit the internal session ID in real workspaces; the synthetic test result retains it for regression fixtures.
- An authenticated staging user can open Sumsub's WebSDK from the account page. Token issuance and refresh call the same-origin API. The adapter signs API requests, verifies webhook digests, and records sandbox review, reset, hold, level-change, deactivation, deletion, and activation events in the durable provider inbox. Signed reset, hold, level-change, deactivation, deletion, and RED review events immediately revoke adult access. Only a reviewed GREEN or activation event can restore it after a fresh provider read; later revocation events fence older approvals. The worker checks Sumsub's current applicant and review before granting or rejecting adult status. Manual test webhooks are rejected. The worker's grant path remains disabled until `SUMSUB_AGE_18_LEVEL_CONFIRMED=true` is set after the sandbox level and permissions are inspected.

## Private staging setup

1. The staging hostname, private Caddy ingress, isolated PostgreSQL/Redis, and initial database migrations are installed on the VPS. Set `BETTER_AUTH_URL` to that HTTPS origin; set `NEXT_PUBLIC_JUNCTION_RUNTIME_MODE=staging` and `NEXT_PUBLIC_JUNCTION_API_URL=/v1` at web build time; use the host-generated `DATABASE_URL` and `BETTER_AUTH_SECRET`. Allow Sumsub's frame, camera, and microphone in the staging host's security headers. Recheck and apply later migration heads before each application release.
2. Verify the sending domain with Resend. Set `RESEND_API_KEY` and `RESEND_FROM_EMAIL` in the deployment secret store. Confirm a real mailbox receives verification and recovery messages.
3. Create a Sumsub sandbox verification level that enforces age 18 or older, and obtain sandbox application token with View applicants permission, API signing secret, and a distinct webhook digest secret. Set `SUMSUB_AGE_LEVEL`, `SUMSUB_APP_TOKEN`, `SUMSUB_SECRET_KEY`, and `SUMSUB_WEBHOOK_SECRET` in the deployment secret store. Configure signed `applicantReviewed`, `applicantReset`, `applicantOnHold`, `applicantLevelChanged`, `applicantDeactivated`, `applicantDeleted`, and `applicantActivated` webhooks. After inspecting the level's age rule and completing a sandbox approve, reject, reset, deactivation, activation, deletion, and replay rehearsal, set `SUMSUB_AGE_18_LEVEL_CONFIRMED=true` for the worker. Never put secret values in the repository or chat.
4. After applying `prisma/migrations/20260925000000_real_platform_reviewer_grants`, sign in the invited reviewer, verify email, complete Sumsub, and enroll MFA. Set `STAGING_REVIEWER_EMAIL` and `STAGING_OPERATOR_LABEL` in the host's protected environment and run `pnpm staging:reviewer grant`. Use `pnpm staging:reviewer revoke` to remove access. The CLI requires `JUNCTION_RUNTIME_MODE=staging` and `DATABASE_URL`; do not run it against the portfolio or local database. Verify queue access and a fresh MFA challenge; then revoke and verify denial without changing application, audit, or outbox state.
